Illustrative curriculum sample / Web development

A clear line from outcomes to evidence.

A three-module sequence that connects program outcomes, an applied project, and evidence faculty can assess.

About this example. This is a newly authored demonstration of curriculum design. It is not an institutional assignment, an adopted program, or a report of student results. Outcome statements and scoring conventions are illustrative and would be agreed with faculty.

01 / Design brief

Build an events application.

The learning challenge

Students may reproduce an interface without being able to explain its connection to application data or demonstrate how it behaves when a request fails. This sequence makes those decisions and checks visible.

Starting conditions

Students can write basic JavaScript, build a simple HTML interface, and use version control. Faculty provide a small React/TypeScript starter, an Express API, and synthetic event fixtures.

Illustrative program outcomes

P1 / Implementation
Build and test a working web application that exchanges data with an API.
P2 / Technical judgment
Explain design choices and use synthetic data responsibly in a development environment.
P3 / Communication
Communicate implementation and verification evidence so another person can reproduce the work.

What this map can tell a program team

Each outcome has a planned place for independent demonstration. The map also identifies where feedback occurs before the final assessment. It describes intended coverage; student evidence is still needed to evaluate attainment.

03 / Applied assessment

Assess the work and the reasoning.

Student submission

Submit the source code and setup instructions; a test matrix with expected and observed results for normal, loading, empty, and failed requests; an annotated demonstration; and a short explanation of design choices and synthetic-data use. A captioned recording or an equivalent text-and-screenshot walkthrough can provide the demonstration.

Use four performance levels: 3 / Accomplished, 2 / Meets expectations, 1 / Developing, and 0 / No assessable evidence. Level 0 applies when evidence for that criterion is absent or cannot be evaluated.

P1 · 35% of project score

Application & data flow

3 / Accomplished
Data flows correctly from the provided API to the interface; the implementation also validates the expected response shape and handles an unexpected payload.
2 / Meets expectations
The interface retrieves and displays the provided event data correctly, with a traceable request and response.
1 / Developing
The connection is incomplete, relies on hard-coded display data, or contains errors that prevent reliable use.

P1 · 30% of project score

Behavior & verification

3 / Accomplished
All four required states are verified with repeatable checks; an additional malformed-response or recovery case is tested and explained.
2 / Meets expectations
Normal, loading, empty, and error states work; the test matrix records expected and observed behavior for each.
1 / Developing
One or more required states is missing, or the submitted checks do not support the claimed behavior.

P2 · 20% of project score

Reasoning & data handling

3 / Accomplished
Compares a credible alternative, explains a tradeoff using observed behavior, and identifies limits of testing with synthetic data.
2 / Meets expectations
Explains the request flow and key state-handling choices; uses synthetic data and keeps credentials out of submitted files.
1 / Developing
Provides unsupported explanations, cannot trace the request, or does not follow the specified data-handling constraints.

P3 · 15% of project score

Reproducible communication

3 / Accomplished
A peer can reproduce the work from the documentation; the explanation connects test evidence to decisions and identifies remaining limitations.
2 / Meets expectations
Setup instructions and an annotated demonstration let a reviewer run the application and follow the submitted checks.
1 / Developing
Setup steps or evidence are incomplete, or the demonstration does not explain how the work was verified.

Illustrative scoring: for each criterion, multiply its weight by the level earned divided by 3, then add the four contributions for a score out of 100. Faculty set grading thresholds and any required minimum criteria before delivery. Record criterion levels separately so a total score does not obscure gaps in individual outcomes.

04 / Faculty handoff

Make the design teachable and maintainable.

  1. Prepare the environment

    Select and document supported tool versions. Check the starter and synthetic fixtures in the institution's teaching environment. Provide fixtures for empty and failed requests so students can demonstrate each state consistently.

  2. Review access and assessment

    Check keyboard use, readable state messages, accessible document structure, and captioned instructions. Confirm an equivalent text-based demonstration route and align accommodations with institutional practice.

  3. Calibrate before grading

    Faculty apply the rubric to the same practice submission, compare criterion levels, and resolve ambiguous descriptors. Confirm the grading scale and acceptable evidence formats before students begin.

  4. Use evidence to choose the next change

    Review criterion-level patterns after delivery. For example, weak verification evidence could prompt a revised testing activity in Module 2. Record the change, its reason, and the next review point.

A proposed implementation package

An engagement could pair this design with editable module instructions, a starter repository, synthetic fixtures, instructor notes, LMS-ready content, and a revision log. This public sample contains the map, rubric, and planning notes; it does not include a runnable application or institution-specific LMS package.
